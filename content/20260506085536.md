在大模型应用落地的浪潮中，RAG（检索增强生成）已成为企业级 AI 系统的标配架构。然而，很多团队在初步跑通 Demo 后便陷入瓶颈：召回的文档与问题相关性差、答案幻觉频发、复杂问题无从应对。本文将深入拆解 RAG 从基础到进阶的完整升级路径，聚焦多路召回与重排序两大核心技术，帮助你将知识库问答系统的准确率提升到新台阶。

## 一、朴素 RAG 的局限：为什么你的知识库"答非所问"

最基础的 RAG 流程极为简单：将文档切块 → 向量化存储 → 用户提问时向量相似度检索 → 拼接 Top-K 文档给 LLM 生成答案。这个流程在文档质量高、问题简单的场景下表现尚可，但一旦进入真实业务，便会暴露三大致命弱点：

1. **语义漂移**：向量相似度高不等于信息真正相关，"苹果手机"和"苹果公司"在嵌入空间中距离很近，却可能指向完全不同的文档。
2. **关键词失忆**：纯向量检索对专有名词、产品型号、人名等精确词汇不敏感，用户问"GPT-4o 的 token 上限是多少"，召回的却是泛泛介绍 LLM 的段落。
3. **单路召回盲区**：用一种方式检索，就必然存在系统性遗漏。问题本身的歧义性、文档的分散性，都会让单路检索"漏网"。

## 二、多路召回：让不同检索策略"各取所长"

RAG 2.0 的第一个核心升级是**混合检索（Hybrid Retrieval）**，即同时运行多条检索通道，再对结果进行融合。

### 2.1 三路经典组合

| 检索通道 | 原理 | 适合场景 |
|---|---|---|
| 向量检索（Dense Retrieval） | 语义相似度，FAISS/Milvus/Weaviate | 语义理解、模糊问答 |
| BM25 关键词检索（Sparse Retrieval） | TF-IDF 权重精确匹配 | 专有名词、精确短语 |
| 知识图谱检索 | 实体关系推理 | 多跳问答、关系型问题 |

在工程实践中，最常用的是**向量 + BM25 双路融合**，通过 RRF（Reciprocal Rank Fusion）算法将两路排名合并：

```python
def reciprocal_rank_fusion(rankings: list[list[str]], k: int = 60) -> dict[str, float]:
    """
    RRF 融合多路检索结果
    rankings: 每路检索返回的文档 ID 列表（按排名排序）
    k: 平滑参数，默认 60
    """
    scores = {}
    for ranking in rankings:
        for rank, doc_id in enumerate(ranking):
            if doc_id not in scores:
                scores[doc_id] = 0.0
            scores[doc_id] += 1.0 / (k + rank + 1)
    return dict(sorted(scores.items(), key=lambda x: x[1], reverse=True))
```

### 2.2 查询扩展：一个问题，多种问法

多路召回还可以从**查询侧**做文章。利用 LLM 将用户原始问题改写为多个不同表述，分别检索后合并，能显著提升召回率：

```python
from openai import OpenAI

def expand_query(original_query: str, n: int = 3) -> list[str]:
    """使用 LLM 扩展查询"""
    client = OpenAI()
    prompt = f"""请将以下问题改写为 {n} 个不同角度的版本，保持语义一致，仅返回改写后的问题列表，用换行分隔：
    
原始问题：{original_query}"""
    
    response = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "user", "content": prompt}]
    )
    variants = response.choices[0].message.content.strip().split("\n")
    return [original_query] + [v.strip() for v in variants if v.strip()]
```

## 三、重排序（Reranking）：精准过滤的"第二道关口"

多路召回解决了"捞得够宽"的问题，但捞上来的文档依然可能鱼龙混杂。**重排序模型（Cross-Encoder Reranker）**就是这道精准过滤关口。

![数据处理与模型推理流程](https://images.pexels.com/photos/1181244/pexels-photo-1181244.jpeg?auto=compress&cs=tinysrgb&w=800)

与向量检索中用于粗排的 Bi-Encoder 不同，Cross-Encoder 会将**问题+文档**拼接后一起输入模型，计算真实相关性分数，精度远高于向量余弦相似度，代价是计算开销更大，因此只用于对 Top-N 候选文档二次精排。

```python
from sentence_transformers import CrossEncoder

reranker = CrossEncoder("BAAI/bge-reranker-v2-m3")

def rerank_documents(query: str, candidates: list[dict], top_k: int = 5) -> list[dict]:
    """
    使用 Cross-Encoder 对候选文档重排序
    candidates: [{"id": ..., "content": ..., "score": ...}, ...]
    """
    pairs = [[query, doc["content"]] for doc in candidates]
    scores = reranker.predict(pairs)
    
    for doc, score in zip(candidates, scores):
        doc["rerank_score"] = float(score)
    
    return sorted(candidates, key=lambda x: x["rerank_score"], reverse=True)[:top_k]
```

> **经验提示**：重排序阶段通常取初次召回结果的 Top-20 到 Top-50 进行精排，最终取 Top-3 到 Top-5 输入 LLM。过少会丢失优质文档，过多则会稀释信噪比、增加 token 消耗。

## 四、完整 RAG 2.0 工程管道

将上述模块串联，形成一条可落地的生产级管道：

```
用户问题
  ↓
[查询扩展] → 生成 3-5 个查询变体
  ↓
[多路并行召回]
  ├── 向量检索（Top-20）
  └── BM25 检索（Top-20）
  ↓
[RRF 融合] → 合并排名，取 Top-30
  ↓
[Cross-Encoder 重排序] → 取 Top-5
  ↓
[上下文组装] → 拼接文档 + 对话历史
  ↓
[LLM 生成] → 最终答案
```

在实际项目中，这条管道的延迟约在 800ms - 1.5s 之间（使用 `gpt-4o-mini` + `bge-reranker-v2-m3`），对于绝大多数企业知识库问答场景完全可接受。

## 五、进阶：自适应检索与 Agentic RAG

RAG 2.0 的下一个演进方向是**Agentic RAG**：让 LLM 自主决策是否需要检索、检索几次、检索什么内容。核心组件包括：

- **路由器（Router）**：判断问题是否需要检索，还是直接用参数知识回答
- **迭代检索器**：对于复杂多跳问题，先检索一轮，再根据中间答案拆解子问题继续检索
- **自我反思（Self-RAG）**：生成答案时同步生成"是否需要更多证据"的判断标记

```python
# 简化版 Agentic RAG 决策逻辑示意
def should_retrieve(query: str, llm) -> bool:
    """让 LLM 判断是否需要外部检索"""
    decision = llm.invoke(
        f"判断以下问题是否需要查询外部知识库才能准确回答（仅回答 YES/NO）：\n{query}"
    )
    return "YES" in decision.upper()
```

## 六、总结

RAG 从 1.0 到 2.0 的升级，本质上是从"单点优化"走向"系统工程"。多路召回扩大了信息覆盖面，重排序保证了精准度，查询扩展弥补了语义鸿沟，三者协同才能构建真正可用的生产级知识库系统。

**关键数据参考**：在多个企业级项目实测中，从朴素 RAG 升级到多路召回 + 重排序方案后，答案准确率（Top-1 Hit Rate）通常提升 **15% - 30%**，幻觉率降低约 **40%**。

如果你的团队正在构建知识库问答、企业搜索或 AI 客服系统，RAG 2.0 的技术栈已经足够成熟，值得作为基线方案认真落地。
